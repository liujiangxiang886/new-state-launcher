# 规范手册（1.7 事实基准）

> 这份文档是**可机读的事实基准**：`tools/check_doc.py` 会逐条核对这里的映射、
> 正则、状态值与代码是否一致。改代码后如果这里没跟上，脚本会报红。
> 面向维护者；玩家看 `玩家须知.md`，作者看 `扩展开发文档/`。

---

## 1. 基础概念

| 概念 | 定义 |
|---|---|
| 引擎线 | 一条独立的运行链路：引擎版本、基线、源码层、mod 集合、存档目录都不同。当前 4.6 / 4.7 |
| 基线 | 一份具体本体 + 它的源码层。id 形如 `jjxf.v1.45` |
| 扩展 | 装在 `packs/<id>/` 下的覆盖层 + 清单，参与启动组装 |
| 剧情层 | 4.7 的源码/内容覆盖层，挂在基线与 mod 之间 |
| 插桩 | 把 `dispatch_before/after` 写进原脚本明文，再打成覆盖层 |
| 「安装成功」≠「实际生效」 | 前者只看文件层；后者要启动一次、看状态是否翻成已就绪 |

### 1.1 四条不变量

1. 一条线一份覆盖层、一份清单副本、一个启用位。
2. 跨线安装硬拒绝，不做「试着装装看」。
3. 依赖源码的包在本线没有可信源码时拒装。
4. 状态只有 `ready`（已就绪）与 `needs_hooks`（待插桩）两种主状态。

## 2. 双基线规范

| 引擎线 | 基线 id | 基线别名 | pack 版本 | 源码包 |
|---|---|---|---|---|
| 4.6 | `jjxf.v1.45` | `jjxf.v1.45.original` / `v1.45` / `1.45` | 4.6 → 3 | `sources-4.6.zip` |
| 4.7 | `jjxf.v4.7` | `jjxf.v4.7.story` / `v4.7` / `4.7` | 4.7 → 4 | `sources-4.7.zip` + 剧情层 |

- 基线 id 与 `engine.line` 必须自洽；不一致在清单校验就是 error。
- 4.7 标准本体：380,259 条目 / 3,066,540,271 字节；不符则源码层不使用。
- 基线条目可带 `story_overlay`（4.7 剧情层），相对路径用 `resolve_path` 解析。

## 3. 兼容协议

- 清单 schema 1 / 2 / 3 / 4 都能读；4 = 3 + 强制 `sources`。
- `requires` 缺依赖 → 拒绝启动；`conflicts` 命中 → 拒绝启用。
- 位置级冲突用 `overrides` + `expect` + `requires` 三条件解除；缺一不可。
- 联机协议（P2P / ENet / WebSocket / UDP / TCP / DTLS / 自建服务端 / NAT 穿透 /
  局域网发现）一律拒绝。
- 跨线重算补丁不视为兼容：硬拒绝。

### 3.1 校验档

| 档 | 安装 | 启动 |
|---|---|---|
| `loose` 宽松校验 | 全套检查照跑；error 记录但照装（`_LAUNCHER_FATAL` 除外） | 有风险提示，玩家可继续 |
| `strict` 完全校验 | 任何 error 拒装；冲突未处置拒装 | 启动前确认剔除名单 |

`verified` 表示「这个包曾经通过一次真实挂载冒烟」，不是「永久可信」；
`verify_smoke` 是安装时是否强制跑冒烟，默认单包 True、批量 False。

## 4. 扩展规范

### 4.1 清单

必填：`schema`、`id`、`name`、`version`。
强条件：有 `text_patches` / `method_hooks` 时 `sources` 必填（schema 4）。

id 正则（与代码逐字符一致）：

```
^[a-z0-9][a-z0-9._-]{1,63}$
```

### 4.2 加载波次

| kind | 波次 |
|---|---|
| `framework` | 0 |
| `extension` | 1 |
| `mod` | 1 |
| `theme` | 3 |

`priority` 越小越先；同 kind 再按 `load_after` / `load_before` 排序。

### 4.3 改动方式优先级

`files[]` > `data_patches[]` > `text_patches[]` > `method_hooks[]`
（越靠前越稳；能改数据就别改脚本）。

### 4.4 源码

`text_patches` / `method_hooks` 的原文来源：
反解工程 → 剧情层（4.7）→ 基线 pck 明文 → 随包源码 → 已装扩展覆盖层。

`sources` 三字段：`name`、`sha256`、`line`；sha256 不符即拒装。

---

## 5. 剧情包规范

- 形态：`.pck`，包含 `scripts/`（`.gd` + `.remap`）、`scenes/`、`data/`。
- 单文件上限 **32 MB**，超限跳过并记录 issue。
- 挂载：`baseline → story → mod → sources → merged → instrumented`。
- 剧情层优先于随包源码：同名脚本以剧情层为原文。
- 两种交付：剧情覆盖层（可挂 mod）/ 合并基线（单包、无 mod）。
- 替换剧情层会让按旧源码算的补丁失配，必须先停用该线扩展。

---

## 6. 挂载与冲突

### 6.1 顺序

```
baseline pck
  → story overlay（4.7）
  → 各扩展 overlay（按解析顺序）
  → sources 兜底层（补 .gd 依赖与子类）
  → merged（多扩展改同一文件时叠加）
  → instrumented（钩子插桩，必须最后）
```

### 6.2 判定级别

| 级别 | 含义 | 处置 |
|---|---|---|
| L1 | 文件层完整，可挂载 | 正常 |
| L2 | 补丁部分命中 / 位置级降级 | 提示；strict 拒装 |
| L3 | 钩子未注册 / 待插桩 | 启动后验证 |
| L4 | 与已启用包冲突（claims / 位置 / 依赖） | 拒装或剔除 |

### 6.3 claims

`rule:<系统>.<规则>` / `ui:<区域>.layout` 同键即冲突，不可豁免。

## 7. 存档隔离

- 每条线/实例一个 `user://` 目录；`profiles/<名字>/`。
- 启动前备份到 `.history/<时间戳>/`；退出后 diff 并写摘要。
- 导入存档/角色前先备份。
- 启动器的 `profiles/` 与游戏的 `user://` 通过配置映射；不写系统目录。

## 8. 目录与文件布局

```
config/         launcher.json、extensions.json、stories.json、decisions.json
baseline/       sources-4.6.zip、sources-4.7.zip、identity-*.json、index-*.json.gz
engines/        godot-4.6 / godot-4.7 引擎

```

覆盖层命名规则：`overlay-46.pck` / `overlay-47.pck` / `overlay-custom_<id>.pck`
（一律经 `paths.line_tag()`）。

### 8.1 临时文件：一律在 D 盘，不写 C 盘

硬约定：**依赖、缓存、临时目录、构建产物都不放 C 盘**（系统盘只装系统和 IDE）。

| 场景 | 落在哪 | 谁保证 |
|---|---|---|
| 跑测试（`pytest`） | `_build_tools/tmp/pytest/run-<时间>-<pid>/` | `tests/conftest.py` 启动时把 `TMP`/`TEMP`/`TMPDIR` 与 `tempfile.tempdir` 全部改到项目内，并给每轮单独开子目录 |
| `jjm_pack.py verify` 解合集 | **包所在目录**下的 `jjm-verify-*`（用完即删） | `temp_workspace()`；`JJXF_TMP` 可显式指定，只读介质才退回系统 Temp |
| PyInstaller 中间物 | `builds/_pyi*`（`--workpath`） | 构建命令显式传参 |
| 安装/启动中间物 | `builds/` | `paths.BUILDS` |

> 只设 `--basetemp` **不够**：`tempfile` 走的是 `TMP`/`TEMP`，默认指
> `C:\Users\<用户>\AppData\Local\Temp`。任何一处 `tempfile.mkdtemp()` 都会绕回去，
> 所以 conftest 里连 `tempfile.tempdir` 一并覆盖。
>
> **basetemp 必须每轮换子目录**（`run-<时间>-<pid>`）。pytest 启动时会
> `rm_rf` 整个 basetemp；2026-11-13 D 盘写满时，上一轮有个目录删不掉
> （`WinError 5`），结果当轮 **747 个用例全部在 setup 阶段报 error**，
> 一条真失败都看不出来。换子目录后，脏的东西只脏它自己那一轮。
> 旧轮次由 `_sweep_old_runs()` 回收（超过 2 小时的才删，避免踩到并发会话）。
>
> 外部工具链（PyInstaller、pip）默认也会用系统 Temp；跑它们前把 `TMP`/`TEMP`
> 指到 `_build_tools/tmp` 即可（`PYINSTALLER_CONFIG_DIR` 如需缓存也指到项目内）。

### 8.2 跑全量测试：三个「环境坑」必须知道

这三条都不是产品缺陷，但都会让测试**看起来全红**、**退出码乱掉**或者
**把真实数据写坏**，排查时极容易误判成代码坏了。`tests/conftest.py` 已经处理，
这里记录原因。

**(1) 宿主的 safe-delete 壳会把会话打崩。**

开发机上的 `sitecustomize.py` 会给 `shutil.rmtree` / `os.remove` / `Path.unlink`
套一层保护：删除先进回收站，且**本轮累计删除满 50 次就 `raise SystemExit(1)`**。
而 pytest 的 `tmp_path` 在**每个通过用例结束时**都要删一次临时目录 ——
一轮 740+ 个用例，删到第 50 个就撞钩子：

```
ERROR at teardown of test_xxx - SystemExit: 1
...
INTERNALERROR> ValueError: '<项目根目录>' is not in the subpath of '<项目根目录>'
119 failed, 391 passed, 166 errors
```

注意最后的报错本身是假的 —— 会话状态被 `SystemExit` 搞坏之后，pytest 在
生成报告路径时自己崩的。**测试代码一直是全绿的。**

`SystemExit` 不是 `Exception`，所以 `rmtree(..., ignore_errors=True)` 也兜不住它，
这也是它能把整个进程带走的原因。

对策：`conftest._restore_stock_delete()` 把删除函数换回标准库原版。
壳把原始实现藏在函数局部变量里（外部拿不到），所以做法是：从 `nt` / `posix`
取原生 `remove`/`unlink`/`rmdir`，修好 `os` 之后 `reload(shutil)`，再扫一遍
已加载模块里「早期 `from shutil import rmtree` 留下的旧引用」（`_pytest.tmpdir`
就是这种）。报告头会打印确认：

```
temp: <项目根目录>\_build_tools\tmp
safe-delete: shutil.rmtree / os.remove / Path.unlink 已还原；另外修正了 1 处早期 import（_pytest.tmpdir）
basetemp: <项目根目录>\_build_tools\tmp\pytest\run-20261113-152205-33312
```

**另一个必须做的原因**：产品里本来就有卸载/清理逻辑（删扩展目录、删 overlay 层）。
套着这层壳去测，断言拿到的是「壳拒绝了删除」，测的根本不是产品行为。

**(2) 界面测试留下没销毁的控件 → access violation，退出码变成 3221225477。**

`deleteLater()` 只是**排队**删除。测试里没有事件循环，没人派发 `DeferredDelete`，
控件一直活到解释器退出；shiboken 再去析构 C++ 对象就
`Fatal Python error: Aborted` + `Windows fatal exception: access violation`。

可怕的地方在于：报告明明写着 `747 passed, 1 skipped`，但进程退出码是
`3221225477`（`0xC0000005`）/ `3221226505`（`0xC0000409`），脚本和 CI 一律判定失败。

正解是**在测试里真的销毁** —— 统一走 `tests/qt_cleanup.py`：

```python
from qt_cleanup import dispose
dispose(*pages)     # close → setParent(None) → deleteLater → 派发 DeferredDelete
```

反面教材（都试过，都不行）：

- 在 `pytest_unconfigure` 里遍历 `QApplication.allWidgets()` 会**当场崩** ——
  列表里包含刚 `deleteLater` 过的半销毁对象，一碰就是 access violation；
- 只调 `QApplication.shutdown()` 不销毁控件：能把崩溃概率降下来，但**不是确定性**的
  （同一套用例连跑两次，第二次仍会 abort）。

`pytest_unconfigure` 里保留 `shutdown()` + `os._exit(真实退出码)` 只是**兜底**，
用来保证「万一还有控件没销毁，退出码也不会变成假失败」；根治仍然靠测试自己销毁。
调试时想看真实退出路径，设 `JJXF_TEST_KEEP_PROCESS=1`。

**(3) 测试默认会写真实的 `packs/` / `builds/` / `config/`。**

`service.install()`、`uninstall.purge_line_workdirs()`、`housekeeping.sweep()`
都直接读写运行期目录。2026-11-13 实测：跑一轮全量之后，

- 真实 `packs/` 里堆了 30+ 个 `mod.a` / `test.member` / `test.gate.*` 测试包；
- 真实 `config/extensions.json`（**已装扩展清单**）被覆盖成 2 条测试数据
  —— 本机 28 个已装扩展（4.6 线 25 个、4.7 线 24 个）当场全丢；
- `config/verified.json` 被写成 `good.ext` / `old.ext` 的假验证记录。

对策：`conftest._isolate_runtime_dirs` 是 **autouse** 夹具，每个用例默认
把 `BUILDS` / `PACKS` / `CACHE` / `service.REGISTRY` / `verify_mark._local_path`
指到 `tmp_path` 下。确实需要读真实目录的用例，显式打标记退出隔离：

```python
@pytest.mark.real_dirs
def test_xxx(): ...
```

**隔离的死角：写死的路径常量。** 隔离改的是 `paths.BUILDS`，模块级
`WORK = ROOT / "builds" / "xxx"` 这种常量在 import 时就算好了，补丁对它无效。
三个真引擎用例（`test_ctx_extended` / `test_hook_overwrite` /
`test_mod_host_isolation`）就这么干过：每个 case 拷一份 164 MB 的 `jjxf46.exe`，
**一轮全量往真实 `builds/` 里写 1.5 GB**（实测 `mod-host-isolation` 821 MB、
`hook-overwrite` 328 MB、`ctx-extended` 328 MB）。

判据：新建测试目录时**调用时取路径**，不要写常量。

```python
def _work_dir() -> Path:          # ✅ 跟着 monkeypatch 走
    return paths.BUILDS / "xxx"

WORK = ROOT / "builds" / "xxx"    # ❌ 绕过隔离，每轮往真实目录写
```

**验收标准**（五条一起看，缺一条都可能被假象骗过去）：

1. `748 passed, 1 skipped`；
2. 进程退出码 `$? == 0`（不是 127/3/3221225477）；
3. stderr 里没有 `fatal exception` / `Fatal Python error`；
4. 跑完之后 `config/*.json` 的哈希不变（真实数据没被写）；
5. 跑完之后 `du -sh builds` 不增长（增长说明有测试绕过了隔离）。

## 9. 故障排查

| 现象 | 先查 |
|---|---|
| 装不上 | 清单 error、源码声明、跨线、schema |
| 装上了没反应 | 状态是否 `needs_hooks`；日志「插桩」「合并层跳过」 |
| 黑屏 | 最近装的扩展；`files[]` 是否铺了原版脚本 |
| 卸载后还在 | 插桩缓存；用「清理残留」 |
| 4.7 补丁全失配 | 是否用了 4.6 锚点；剧情层是否换过 |
| 提示源码不符 | 本体是否标准版；反解工程是否匹配 |
| 测试一片 `SystemExit: 1` / `INTERNALERROR` | 宿主 safe-delete 壳没还原，见 §8.2 |
| 测试全绿但退出码 127/3/3221225477 | 界面测试没销毁控件（`deleteLater` 不够），见 §8.2 |
| 跑完测试已装扩展清单没了 | 测试没隔离 `packs/` / `extensions.json`，见 §8.2(3) |

## 10. 已知问题与待解决事项

### 10.1 显示已安装但功能不生效

**触发条件**：钩子目标脚本不在源码里；方法名写错；合并层锚点失配；
源码指纹不符导致整层跳过。

**复现步骤**：装一个 `method_hooks` 指向不存在方法的包 → 启动 → 状态仍是
`needs_hooks` → 游戏内无变化。

**环境信息**：启动器 1.7；线 4.6/4.7；本体指纹；日志中「插桩」相关行。

**临时规避**：停用该包；或让作者按本线源码修正方法名/锚点。

### 10.2 其他待办

- 自定义线的插桩层生成器未接入（目前 `probe-only`）。
- 4.7 剧情层差异未纳入 `sources` 校验（靠 `x_story` 备注）。
- 扩展页的补丁明细仍以 tooltip 呈现，长列表不易读。

## 12. schema 1 → 2 映射

| 旧写法 | 新写法 |
|---|---|
| `schema` | `schema: 1 → 2` |
| `baseline` | 字符串 → `{id, engine.line}` |
| `entry` | → `scripts.entry` |
| `files[].expect_sha256` | → `files[].expect.sha256` |
| `data_patches[].operations` | → `ops`；`set` → `replace` |
| `text_patches[]` | 补 `mode=literal`、`expect_count=1` |
| `script_members` | → `scripts.members` |
| `project_settings` | → `settings.project` |
| `input_actions` | → `inputs.actions` |
| `requires` | 字典 → 列表 |
| `method_hooks[]` | 补 `phase=after`、`priority=50`、handler 由运行期注册 |

## 13. 相对路径

清单/配置里的路径可以是绝对路径，也可以相对项目根；统一用 `resolve_path`
展开。`target` 里出现 `..` 一律拒绝（安全底线）。`res://` 前缀在读原文时自动剥离。
