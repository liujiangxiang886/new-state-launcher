# 4.7 线 · 1.45 剧情版 mod 开发规范（含剧情 mod）

> 适用：**新起点启动器 1.7** · 4.7 引擎线（机甲旋风 1.45 剧情版 · Godot 4.7.2）
> 基线：`jjxf.v4.7`（标准本体 **380,259 条目 / 3,066,540,271 字节**）
> 清单：`extension.json`（`manifest-47.v2.json` 也认）
> 规范版本：**1.7**（schema **4**）　配套工具：`tools/jjm_pack.py`

---

## 0. 4.7 不是「4.6 加了点剧情」

实测同一路径的脚本被整段重写：

```
4.6  scripts/hud.gd = 18,011 字节
4.7  scripts/hud.gd = 32,067 字节    ← 几乎翻倍
```

同一个函数头 `func _ready() -> void :`，函数体完全不同。**4.6 的 `text_patches`
锚点在 4.7 上大概率失配；即使命中，改的也可能不是同一个函数。**

| 改动方式 | 4.6 → 4.7 要重做吗 | 原因 |
|---|---|---|
| `files[]`（自己的文件） | 不用 | 与基线无关 |
| `method_hooks` | 基本不用 | 方法名没变 |
| `data_patches` | 要核对 | 4.7 新增了大量数据字段 |
| `text_patches` | **必须重做** | 必须按 4.7（或剧情层）的源码重算 |

## 1. 分线隔离：两条线各自独立

| 项目 | 4.6 | 4.7 |
|---|---|---|
| 安装目录 | `packs/<id>/overlay-46.pck` | `packs/<id>/overlay-47.pck` |
| 清单副本 | `manifest-46.v2.json` | `manifest-47.v2.json` |
| 启用状态 | 独立 | 独立 |
| 卸载 | 只删 46 那份 | 只删 47 那份 |
| 源码层 | `sources-4.6.zip` | `sources-4.7.zip` + 剧情覆盖层 |

**同一个包要支持两线，就出两份清单**，放在同一个 zip：

```
me.my_ext-1.2.0.zip
├─ manifest-46.v2.json
├─ manifest-47.v2.json
└─ payload/            ← 共用载荷
```

- 两份清单各自声明自己的 `baseline` / `engine.line` / `sources` / `text_patches`。
- **不要**改 46 那份来适配 4.7。
- 在 4.6 停用这个包，不会影响 4.7 的启用状态；反之亦然。

> 跨线安装是**硬拒绝**：4.6 的包装到 4.7 会直接失败，不会「试着装装看」。

## 2. 源码兜底：4.7 比 4.6 更依赖它

4.7 原版 pck 里的脚本只有 `.gdc`，没有 `.gd`。启动器随包带：

```
baseline/sources-4.7.zip     ← 138 个 .gd（与 4.7 标准本体逐字节一致）
baseline/sources-4.7.json    ← 本体指纹：entry_count=380259 + pck_size + sha256
```

取原文顺序（`basecontent.py`）：

1. 设置里指向的反解工程
2. **剧情覆盖层**（`story_overlay`，4.7 真正的源码/内容层）
3. 基线 pck 里的明文（4.7 基本没有）
4. **随包源码 `sources-4.7.zip`**
5. 已安装扩展的覆盖层

### 2.1 清单声明

```jsonc
"baseline": { "id": "jjxf.v4.7", "engine": { "line": "4.7" } },
"sources": {
  "name": "sources-4.7.zip",
  "sha256": "用 jjm_pack.py manifest --line 4.7 自动生成",
  "line": "4.7"
}
```

规则与 4.6 相同：

- 用了 `text_patches` / `method_hooks` 就必须写；schema 4 没写直接拒装。
- `sha256` 与随包源码不一致 → 拒装（按另一份源码算的锚点）。
- **非标准本体**（条目数不是 380,259、pck 大小不符）会被指纹判定拦下：那种本体的脚本可能已经改过，随包源码不再可信。先换标准本体，或在设置里指向与它匹配的反解工程。

### 2.2 剧情层是「第一原文」

如果目标脚本在剧情覆盖层里存在，**剧情层优先于随包源码**。也就是说：

- 打 `scripts/xxx.gd` 的补丁，锚点要按**当前剧情层里的那份文本**算；
- 换过剧情包之后，旧锚点可能失配——这正是「替换剧情包」界面会警告的原因；
- `sources` 声明的是基线源码版本，剧情层的差异要用 `x_story` 之类的自定义字段记录（启动器不解析，但排障时有用）。

## 3. 剧情 mod（4.7 专属）

「剧情 mod」不是普通扩展。它替换/追加的是 4.7 的**剧情覆盖层**，也就是这条线的
源码层与内容层，挂载顺序在 mod **之前**：

```
baseline(4.7 本体) → story(剧情层) → mod overlay × N → sources 兜底层 → merged → instrumented
```

### 3.1 剧情层是什么

一个 `.pck`，通常包含：

```
scripts/…      同名 .gd 源码 + .remap（中和本体的 .gdc）
scenes/…       .tscn / .tres
data/…         JSON / 配置
uid_cache.bin  可选
```

- 条目数示例：官方分区·轻量 = **741 条**，约 168 MB。
- 它与本体同名条目会**整片覆盖**；它独有的路径只在剧本/脚本引用时生效。
- 单文件建议 ≤32 MB（打包器会跳过超限文件并记录 issue）。

### 3.2 两种交付形态

| 形态 | 产物 | 适用 | 代价 |
|---|---|---|---|
| **剧情覆盖层**（推荐） | `story.pck`，登记到 `config/stories.json` | 启动器启动，保留 mod 能力 | 玩家需要启动器 |
| **合并基线** | 把剧情层合并进本体，产出单个 `.pck` | 直接用原版 exe 启动、不带启动器 | 合并后**不能再装 mod**（没有挂载器） |

#### A. 剧情覆盖层

登记结构（`config/stories.json`）：

```jsonc
{
  "id": "官方分区-轻量",
  "name": "官方分区·轻量",
  "version": "1.0",
  "line": "4.7",
  "overlay": "packs/story-官方分区-轻量/story.pck",
  "entry_count": 741,
  "total_bytes": 168081190,
  "sha256": "…",
  "include": ["scripts", "scenes", "data"],
  "enabled": true,
  "sources": ["…/scripts.zip", "…/scenes.zip", "…/data.zip"]
}
```

基线条目里用 `story_overlay` 指向它（相对路径按项目根解析）：

```jsonc
"baselines": {
  "jjxf.v4.7": { "engine": "4.7", "story_overlay": "packs/story-官方分区-轻量/story.pck" }
}
```

界面路径：游戏库 → 4.7 → 「4.7 剧情覆盖层」→「替换剧情包…」。
替换会备份旧文件为 `story.pck.bak`，并提示「按旧剧情源码算的补丁会失配」。

#### B. 合并基线（给原版 exe 用）

```bash
python tools/merge_story_into_baseline.py \
  --baseline "…/机甲旋风Demo.pck" \
  --story "packs/story-官方分区-轻量/story.pck" \
  --out "…/机甲旋风Demo.merged.pck" --report out.json
```

- 只重排目录、不动数据字节；同名条目改指向剧情版本。
- 合并产物是**完整包**，原版模板 exe 能直接加载。
- 合并后**没有 mod 层**：启动器不会再往它上面挂扩展。要 mod 就用形态 A。

### 3.3 剧情 mod 作者要守的规则

1. **声明 `line: "4.7"`**，不要把 4.6 的剧情包挂到 4.7 上。
2. **保留同名 `.remap`**，否则本体 `.gdc` 会盖住你的 `.gd`。
3. **不要带本体的完整资源**。只放你改过的脚本/场景/数据；整包铺入会让体积和加载时间爆炸。
4. **换层即失效**：你的 mod 如果按剧情层源码算锚点，玩家换剧情包后补丁可能失配。发布说明里写清「适配哪个剧情版本」。
5. **剧情层不是扩展**：它不进 `packs/<id>/overlay-*.pck`，也不参与扩展的启用/停用；卸载走「删除该线扩展」或手工移除登记。

## 4. 4.7 的 `text_patches` 怎么写

四条铁律与 4.6 相同（`find` 唯一、缩进逐字符、find/replace 一起改、用 `scope` 收窄），
额外注意：

### 4.1 先用源码核对，再写锚点

```bash
python tools/jjm_pack.py check 我的包.zip --line 4.7
```

`check` 会用 `sources-4.7.zip` 验证：

- 每条 `find` 的命中数是否等于 `expect_count`；
- 每个 `method_hooks.target` / `method` 是否真的存在；
- `sources.sha256` 与本机随包源码是否一致。

### 4.2 锚点不唯一：`scope`

4.7 经常出现「通用收尾片段」在多个函数里重复：

```gdscript
	if not persist(before):
		return {}
```

`pet_state.gd` 的 `open_package()` 和 `bank_experience_card()` 各有一份。
`expect_count: 1` 会命中 2 处 → 整条补丁被拒，功能静默缺失。用：

```jsonc
{ "target": "scripts/pet_state.gd", "scope": "function:open_package",
  "find": "…", "replace": "…" }
```

### 4.3 不要把 4.6 的锚点直接搬过来

即使 `find` 还能命中，也要人工确认「改的还是不是那个函数」。4.7 的剧情改写会
移动代码块，锚点可能落在另一个语义位置。

## 5. 打包 / 校验 / 发布

```bash
# 生成 4.7 清单（自动写 sources-4.7.zip 的 sha256）
python tools/jjm_pack.py manifest 我的扩展/ --id me.my_ext --name "我的扩展" --line 4.7

# 静态检查（锚点、钩子、源码声明、联机）
python tools/jjm_pack.py check 我的扩展.zip --line 4.7

# 开发者校验准入
python tools/jjm_pack.py verify 我的扩展.zip --line 4.7

# 打包 + 封验证标记
python tools/jjm_pack.py pack 我的扩展/ -o 我的扩展-1.0.0.zip
python tools/jjm_pack.py seal 我的扩展-1.0.0.zip
```

严格档（`strict`）下：

- 清单任何 error 都拒装；
- 补丁没命中就是失败，不装「半残」的包；
- 与已启用扩展有未处置的位置冲突会拒装。

## 6. 常见坑（4.7 专属）

| 现象 | 原因 | 处理 |
|---|---|---|
| 补丁全部失配 | 用了 4.6 的锚点 | 按 4.7/剧情层源码重算 |
| 锚点命中但功能不对 | 命中了同名的另一个函数 | 用 `scope` 限定；人工核对 |
| 装完提示「本体 pck 大小与随包源码不符」 | 本体不是标准 4.7 | 换标准本体；或指向匹配的反解工程 |
| 剧情更新后旧 mod 失效 | 剧情层整片覆盖，锚点变了 | 按新剧情源码重算，发布新版本 |
| 游戏里剧情没变化 | 剧情包排在 mod 之后被盖 / 没登记 | 确认 `story_overlay` 指向正确；挂载顺序是 baseline→story→mod |
| 合并基线后 mod 全没了 | 合并形态没有挂载器 | 要 mod 就用剧情覆盖层形态 |
| 换剧情包后进游戏黑屏 | 旧 mod 的补丁打在错误位置 | 先停用该线扩展，再换层 |

## 8. 钩子共存：写 `result` 的规矩

同一方法被多个扩展挂钩子是常态（`character_attributes`、`damage` 这类热路径尤其）。
启动器把**同一个 `context` 字典**传给同点的所有回调，所以「各自改了哪些键、怎么改的」
决定了它们能不能共存。这一节是硬约定，不是建议。

### 8.1 一律用「读—改—写」

```gdscript
# 对：叠加。别人先改多少，你读到多少，再往上加
var base: float = float(attributes.get(attr, 0))
attributes[attr] = int(round(base * mult + add))

# 错：直接赋值。谁后跑谁说了算，先跑的那份贡献直接没了
result["2013"] = int(round(float(player.get("crit_rate", 50.0)) * 100.0))
```

判定差别的不是「有没有写同一个键」，而是**右值有没有用到当前值**。
读—改—写 = 可叠加；直接赋值 = 覆盖，会被判 `clash`。

真需要「强制某个值」的开关（例如强制暴击率），请在文档里写清触发条件，
并尽量只在用户显式开启时生效 —— 分析器会把条件一起报出来。

### 8.2 不要整份替换 `result`

```gdscript
context["result"] = {}          # 判 clash：任何键都可能被清掉
context["result"] = 新建的字典   # 同上
```

需要「按自己的一套重算」时，改成在入参上就地改。

### 8.3 `skip_original` 会吞掉同点后续回调

`before` 相位里设 `context["skip_original"] = true` 后，`hook_runtime.gd` 的
`dispatch_before` 会立刻 `return`，**排在它后面的回调一个都不执行**。
这比键覆盖严重：不是值被改，是别人的功能直接不跑。

所以启动器一律判 `clash`（静态分析看不出触发条件）。确实需要时：

- 只在明确的分支里设，不要无条件设；
- 在包说明里写清「什么场景下会跳过原函数」；
- 优先级（第 5 个参数）调大，让自己排在后面，减少吞掉别人的机会。

### 8.4 键名要能被静态枚举

```gdscript
# 可判定：常量表 → 分析器能展开出 2005/2007/...
const KEYS := ["2005", "2007"]
for key in KEYS:
	result[key] = int(result.get(key, 0)) + bonus

# 不可判定：键来自运行期配置 → 只能报「需人工确认」
for key in player_config:
	result[key] = int(result.get(key, 0)) + int(player_config[key])
```

分析器会跟随 `preload` / `class_name` 的跨文件调用（含 `static func`），
所以「钩子只转发、写入在另一个脚本」是允许的，不需要为了可分析而把代码摊平。
但它不猜运行期数据，遇到 §8.4 第二种写法仍会报 `unknown`。

### 8.5 自检

```bash
# 装完后在启动器目录执行：同点共存的结论（safe 不显示）
New\ state\ launcher.exe cli ext-audit 4.7
```

`L0-8` 条目里会写清「谁写了哪个键、是直接赋值还是读—改—写、在什么条件下」。
判定为 `safe` 的同点共存不会出现在输出里 —— 没东西要处理就不占地方。
