# 4.7 扩展适配指南（实战版）

> 适用：**新起点启动器 V1.4**（build `20261113-1750`）· 4.7 线（机甲旋风 1.45 剧情版 · Godot 4.7.2）
> 基准源码：`baseline/sources-4.7.zip`（sha256 `30963972f7f8…`，138 个 `.gd`）
> 工具：`扩展开发文档/tools/jjm_pack.py`
> 本文依据 **2026-11-13 对 49 个社区扩展包的实盘适配**写成（4.7 原生批 22 个 + 4.6 老包批 27 个），每个结论都有复现命令，不是推测。
> V1.4 新增 §9「钩子点共存」：分析器开始跟随 `preload` / `static func` 的跨文件调用。
> 新增 §3.7「源码结构真改了」：这批 4.6 老包有 6 个是源码真的重写了，和换行问题是两回事。

## 0. 先看这三句

1. **4.7 的适配难点不在"写补丁"，在"证明补丁真的生效"。** 启动器有四道关卡，最坑的一种失败是"装上了、界面上没报错、功能静默缺失"。
2. **绝大多数被剔除不是功能问题，是清单问题。** 这批 22 个包全部 `schema 3`、全部声明了 `line=4.7`，功能代码一行没动，却有一半过不了关。
3. **改包之前先跑 `check`。** 它能在 3 秒内告诉你哪一条补丁会失效，比进游戏试快一百倍。

## 1. 什么叫"适配成功"：四道关卡

| # | 关卡 | 命令 | 查什么 | 失败表现 |
|---|---|---|---|---|
| 1 | 静态检查 | `jjm_pack.py check pkg.zip --line 4.7` | 锚点命中数、钩子目标存在、`sources` 一致、schema 合法 | 直接报 `[错误] PATCH-01` 这类，能定位到第几条补丁 |
| 2 | 签封 | `jjm_pack.py seal pkg.zip --line 4.7` | 跑完整 `verify` 后写 `verification.json` | 严格档判 `verify.absent` 剔除 |
| 3 | 安装闸门 | `cli mods install` / 启动器界面 | schema ∈ {1,2,3}、覆盖层在、验证记录有效、位置冲突已处置 | 扩展页状态列显示"已剔除"，日志有 `verify.*` / `conflict.*` |
| 4 | 挂载冒烟 | `cli smoke 4.7 --with-mods` | 覆盖层能否挂上、补丁实际落地数 | `failed_patches` 非空 |

一句话记法：**`check` 过了不代表能装，装了不代表生效。四道都得过。**

还有一道**不拒装**的检查：装完之后两个包挂在同一个方法上（`L0-8` 钩子点共存），
启动器会静态算「各自改哪些键、是不是读—改—写」，结论见 §9。它不影响安装，
只影响「功能会不会被另一个包盖掉」。

严格档（`strict`）才做第 3 道的验证与冲突判定；宽松档（`loose`）放行冲突但仍拒装"根本挂不上"的包（`enable._fits_launcher`）。

## 3. 五类被剔除的真因

按踩坑概率排序。每条都给"怎么确认"和"怎么修"。

### 3.1 锚点带 CRLF，永远 0 命中（最隐蔽）

**这是本次最大的一类，也是唯一会"静默失效"的一类。**

机理链条：

1. `sources-4.7.zip` 里的 `.gd` 是 **LF**；
2. 作者的清单在 Windows 上生成，`text_patches[].find` 里带 `\r\n`；
3. 运行期读源码走 `read_text()`，通用换行把 CRLF 统一成 LF；
4. `patcher._replace_in` 的容错只覆盖**一个方向**（`app/patcher.py:149`）：

```python
if "\n" in needle and "\r" not in needle:          # 锚点是 LF
    pattern = re.compile(r"\r?\n".join(...))       # 能吃 CRLF 源码
    ...
count = region.count(needle)                       # 锚点是 CRLF → 走这条 → 命中 0
```

5. `count == 0` 时 `apply_text` 返回**原文**和空 issues（`patcher.py:196`），日志只留一行"未应用"。

净效果：**补丁看起来写了，实际一条没打，游戏里功能就是没有。**

实测影响：

| 包 | 受影响 | 修前 | 修后 |
|---|---|---|---|
| 挑战模式（qt666） | 7 / 9 条 | `check` 报 7 个 `PATCH-01` | 9/9 全中 |
| 战斗工作台（已剔除） | 36 / 241 条 | 36 个 `PATCH-01` | 241/241 全中 |

**一行自检：**

```python
cr = sum(1 for p in m["text_patches"] if "\r" in p.get("find", ""))
print("CRLF 锚点:", cr, "/", len(m["text_patches"]))
```

**修法**（安全、单向、可批量）：

```python
for p in m.get("text_patches") or []:
    for key in ("find", "replace"):
        if isinstance(p.get(key), str) and "\r" in p[key]:
            p[key] = p[key].replace("\r\n", "\n")
```

`find` 必须归一；`replace` 建议一起归一——留 CRLF 会在 LF 源码里插入混合换行，后续补丁的锚点更难对齐。

> 注：这是**工具链的坑**，不是作者的错。同一份锚点，通过 `jjm_pack.py` 打出来的包是好的，通过某些第三方打包脚本出来的包带 CRLF。见 §8。

### 3.2 没有 `verification.json` → `verify.absent`

严格档第一步就查验证记录（`gate.py:203-216`）：

```python
verdict = verify_mark.judge(cfg, line, pid, root, code_digest=...)
if verdict.ok:
    continue
alive.pop(pid, None)
result.dropped.append(GateDrop(code=f"verify.{verdict.state}", ...))
```

`judge()` 三态：

| 状态 | 含义 |
|---|---|
| `verified` | 包内记录或本地记录的 `code_digest` 与当前启动器代码层指纹一致 |
| `stale` | 有记录，但指纹对不上（换过启动器版本 / 重新打过包） |
| `absent` | 根本没有记录 |

**关键认知：安装器不会替你补记录。** 它只搬运、不签封。开源作者发的 `-47.sealed.zip` 里通常带，随手重新打的 zip 就不带。

本次 8 个缺失：战力系统 + 传奇/经验/装备/副本难度/回复剂/宠物经验/挑战模式 7 个 qt666 包。

**修法：**

```bash
python jjm_pack.py seal pkg.zip --line 4.7
# 输出 pkg.sealed.zip，需要改名回 pkg.zip
```

`seal` 把记录写成独立文件 `verification.json`（不动 `extension.json`，因为启动器对清单字段是严格白名单）。

### 3.3 schema 4 会被本版启动器判"不受支持"

`enable._fits_launcher`（`enable.py:157`）只认 1/2/3：

```python
if schema not in (1, 2, 3):
    return False, f"清单 schema {schema} 不受支持"
```

而《4.7-mod 开发规范》写的是"规范版本 1.7（schema **4**）"。**规范超前于实现**——照着规范把 schema 升到 4，包会在启动阶段被直接剔除，且这个剔除发生在"内容校验"之前，跟补丁写得好不好没关系。

**本版结论：保持 `schema 3`，只补 `sources`。**

`schema ≤ 3` 时 `sources` 缺失只是 `warn`（`SRC-00`），补上则从 warn 变 clean。要不要升 4，等 §8 那处代码改完再说。

### 3.4 `sources.sha256` 填成本体 pck 指纹（`SRC-05`）

`baseline/` 下有**两个不同概念**的哈希，极易搞混：

| 文件 | 字段 | 值 | 含义 |
|---|---|---|---|
| `sources-4.7.json` | `sha256` | `e897b1dc…` | **本体 pck 的指纹**（配合 `entry_count=380259`、`pck_size=3066540271`） |
| `sources-4.7.zip` | 文件本身的 sha256 | `30963972…` | **源码包的哈希** |

清单里 `sources.sha256` 要填**后者**。填前者会得到：

```
[错误] SRC-05 sources.sha256 与本机随包源码不一致（声明 e897b1dc…，实际 30963972…）——锚点是按另一份源码算的
```

**修法：**

```bash
sha256sum baseline/sources-4.7.zip
# 30963972f7f86d95104158962d8329381458ea2ef588ea4018148bcde233959d
```

或者干脆用工具写，别手抄：

```bash
python jjm_pack.py manifest 我的扩展/ --id me.my_ext --name "我的扩展" --line 4.7
```

### 3.5 位置冲突：两个包改同一处（`conflict.location`）

**先纠正一个常见误解：冲突不是"两个包改了同一个文件"。** 同文件、不同位置会自动合并（`overlap.text` 只是 `info`）。真正致命的是"同一处"，判定单位叫 *unit*：

- 文本补丁按 `sha1(find)` 认"同一处"（`units.py:125`）；
- 再加一条"包含"规则：一段锚点整段包含另一段、且短的那段 ≥ 8 字符（`MIN_CONTAIN_LEN`），也算冲突，报作"父子位置"（`units.py:271`）。

本次实例正是第二种：奥莉的锚点是 `"\tif not boss or attack_tick < 0 or hp == 0:\n"`，工作台的是 `"if not boss or attack_tick < 0 or hp == 0:"`——**后者是前者的子串**，只差一个前导制表符和一个换行，肉眼几乎看不出来。

> `check --pair` 在比对前会 `strip()` 锚点，比运行期略严：它把这对判成"同一处"，运行期判成"父子位置"。结论一样（冲突），但两处文案不必完全一致。

流程（`policy.py:190` 起）：

1. `units.discover()` 找出被两个以上扩展改的同一处；
2. 若后包声明了**接管**（`overrides` + `requires` + `expect` 三件套齐全）→ `override`，放行；
3. 否则查 `config/decisions.json` 有没有玩家处置过的记录；
4. 都没有：**严格档判 `error` + `conflict.location` → 剔除**；宽松档降级 `warn`，按加载顺序自动取舍。

本次实例（`check --pair` 的原始输出）：

```
[提示] PAIR-01 mch.treasure_dup 的 text_patches[5] 与 ai_act.combat_workbench 的 text_patches[48]
       撞在同一处：scripts/slice_monster.gd if not boss or attack_tick < 0 or hp == 0:。
       玩家侧默认后者生效；要共存由一方写 overrides + expect 接管 @ scripts/slice_monster.gd
```

两边语义相反：奥莉要"BOSS 也吃硬直"，工作台要"BOSS 有霸体默认不吃"。这一行只能有一个结果。

**处置优先级（从优到劣）：**

| 方案 | 适用 | 代价 |
|---|---|---|
| 收窄锚点（缩到单行 / 加 `scope`）让两者不再重叠 | 语义本来就不冲突，只是锚点框大了 | 需核对替换文本边界 |
| 一方写 `overrides` + `requires` + `expect` 正式接管 | 语义确实冲突，但有明确优先级 | 被接管方必须同时安装 |
| 二选一（本次做法） | 一方有性能/维护问题 | 另一方的对应功能缺失 |

**注意：`check --pair` 只出"提示"，不算 error。** 真正的剔除发生在安装期的严格闸门，所以"check 通过"不等于"能和另一个包共存"——发布前用 `--with` 组合预检：

```bash
python jjm_pack.py verify 我的包.zip --with 别人的包.zip --line 4.7
```

### 3.6 附：包内混着垃圾 zip

战力系统包里根目录套了一个 549 字节的 `mch.power_system-1.2.0.zip`（作者打包时把自己的产物又打进去了），不被 `files[]` 引用。

判据：**根目录 + `.zip` + 不在 `files[].source` 里 → 删。** 启动器不读它，但它会让体积、扫描、玩家误导入都变乱。

### 3.7 源码结构真改了（4.6 老包特有）

3.1 那类是"锚点换行风格不对"，源码本身没变；**这一类是 4.7 真的把这几个函数重写了**，锚点再怎么归一对不上。

判据（和 3.1 区分开）：`find` 归一成 LF 后仍然 0 命中，且 `find` 首行（通常是 `func xxx(` 签名）在 4.7 里**还找得到同名函数，但函数体变了**。

本次 4.6 批 27 个包，10 个非兼容，拆开是：

| 类别 | 数量 | 典型 |
|---|---|---|
| 4.7 已内建同功能 | 3 | 装备兵工厂、机体升级、战斗工作台 |
| **源码结构真改了** | 6 | 全部五位教官、奥莉、宝石镶嵌、宠物经验、挑战模式、六联浮游炮 |
| 4.7 删了补丁落点 | 2 | 挑战模式 1 条、六联浮游炮 1 条数据操作 |
| 只是缺声明（`baseline`/`sources` 还写 4.6） | 23 | 全部 |

**两种修法，别选错：**

1. **按 4.7 新源码重写锚点**（能修）：函数还在、只是上下文变了。
   例：奥莉的 `result.items.append(...)` 那一段，4.7 在 `persist(before)` 前多了一层判断，
   把 `find` 改成带 4.7 新上下文的版本即可，`replace` 逻辑不变。
2. **整包剔除**（修不了，也不该修）：**功能已被官方内建**。
   硬装上去就是把官方新面板覆盖回旧实现，看起来"能用"，实际是降级。判断方法：

```bash
# 看这个功能 4.7 是否已有独立脚本
python - <<'PY'
import zipfile
z = zipfile.ZipFile("baseline/sources-4.7.zip")
print([n for n in z.namelist() if "workshop" in n or "machine_upgrade" in n or "enhance" in n])
PY
```

再确认 `hud.gd` 里有没有对应的 `open_xxx()` 入口被接上。**三个都有 → 一定剔除。**

**容易误判的一条：版本旧 ≠ 该剔除。**
本次把 `qt6663.exp_system` 1.0.1 列进了剔除表，但复查发现 4.7 批里作者已经发了 **1.0.3**
（`几乎完美的原版经验系统（qt666）-1.0.3.zip`，4 条锚点 4/4 命中 4.7 源码）。

这里有个踩坑点：**判断"该不该剔"之前先查有没有新版本**，否则会把"作者已经修好了的功能"当成"必须放弃的功能"报给玩家。

```bash
# 查同名 id 是否已有更新版
python - <<'PY'
import zipfile, json, glob
target = "qt6663.exp_system"
for f in glob.glob("release/*/**/*.zip", recursive=True):
    try:
        z = zipfile.ZipFile(f)
        if "extension.json" not in z.namelist(): continue
        d = json.loads(z.read("extension.json"))
        if d.get("id") == target:
            print(f"{d.get('version'):<10}{f}")
    except Exception:
        pass
PY
```

## 4. 标准流程（7 步）

以下命令都在启动器目录内执行，`TOOLS` 指向 `扩展开发文档/tools`。

```bash
cd "<启动器目录>"
TOOLS="扩展开发文档/tools"
PY="<你的 python>"
OUT="<适配产物目录>"     # Step 6 会用到
```

### Step 1　体检：先拿到全量错误清单

```bash
for f in *.zip; do
  echo "===== $f"
  "$PY" "$TOOLS/jjm_pack.py" check "$f" --line 4.7 | grep -E "^\[错误\]|^结果"
done
```

只看两类行：`[错误]` 和 `结果：`。`[提示]` 先放着。

### Step 2　分诊：按错误码决定改什么

| 错误/提示码 | 含义 | 动作 | 自动化 |
|---|---|---|---|
| `PATCH-01` 命中 0 处 | 锚点按别的源码算的 / 带 CRLF / 基线改了 | 先试换行归一，再核对源码 | 可批量 |
| `PATCH-01` 命中多处于期望 | 锚点不唯一 | 加 `scope:"function:xxx"` | 需人工定函数 |
| `PATCH-02` scope 用不了 | 函数名写错 / 该函数不存在 | 核对 4.7 源码 | 手工 |
| `SRC-00/01` 缺 `sources` | 老包 | 补三字段 | 可批量 |
| `SRC-05` sha 不一致 | 抄了 pck 指纹 | 换成 zip 的 sha | 可批量 |
| `HOOK-01` 钩子目标不存在 | 方法名改了 | 按 4.7 源码改名 | 手工 |
| `SELF-01` 自带文件缺 | `files[]` 指的载荷不在包里 | 补文件 | 手工 |
| `PAIR-01` 位置冲突 | 两包改同一处 | 见 §7 | 需决策 |

### Step 3　修锚点（三条策略，按顺序试）

1. **换行归一**（§3.1）——最便宜，先做，能解决大部分 `PATCH-01`；
2. **`scope` 收窄**——命中多处但某函数内唯一；
3. **按 4.7 源码重写**——锚点彻底失配（4.6 迁 4.7 基本都要走这条）。

重写时不要凭记忆改字符串，直接从源码里抠：

```bash
python - <<'EOF'
from pathlib import Path
src = Path("baseline_src/scripts/flash/dungeon_loot.gd").read_text(encoding="utf-8")
i = src.index("func kill_experience")
print(repr(src[i:i+200]))       # 用 repr 看真实缩进与换行，别用眼睛看
EOF
```

`repr()` 是这一步的关键——制表符和空格在编辑器里长得一样，在补丁里是两回事。

### Step 4　补 `sources`，保持 schema 3

```jsonc
"schema": 3,
"baseline": { "id": "jjxf.v4.7", "engine": { "line": "4.7" } },
"sources": {
  "name": "sources-4.7.zip",
  "sha256": "30963972f7f86d95104158962d8329381458ea2ef588ea4018148bcde233959d",
  "line": "4.7"
}
```

```bash

```

### Step 6　沙盒验证（**不要在原安装目录试**）

为什么必须沙盒：

- 冲突处置会写 `config/decisions.json`（玩家逐项选择的记录），「验证全部」会写 `config/verified.json`。在原安装目录反复试会把这两份搅乱，下次出问题分不清是包坏了还是历史处置残留；
- 冒烟要起真实游戏进程，20 个包一轮十几分钟，中途卡住要能直接杀掉；
- 失败重来时只需清 `packs/` 和 `config/extensions.json`，不用重装整个启动器。

搭沙盒（复制运行必需项，配置清空）：

```bash
Q="../_qa47/New state launcher"
mkdir -p "$Q/config"
cp "New state launcher.exe" "$Q/"
cp -r _internal baseline runtime engines schemas 扩展开发文档 "$Q/"
cp config/launcher.json "$Q/config/"
echo '{"schema":1,"items":[]}' > "$Q/config/extensions.json"
echo '{"schema":1,"items":[]}' > "$Q/config/stories.json"
echo '{"schema":1,"items":[]}' > "$Q/config/minigames.json"
```

装 + 查 + 冒烟：

```bash
cd "$Q"
./"New state launcher.exe" cli mods install "$OUT"/*.zip --line 4.7
./"New state launcher.exe" cli lock 4.7                     # 严格档：看 keep / dropped
./"New state launcher.exe" cli smoke 4.7 --with-mods --ext-mode strict --timeout 300
```

`lock` 输出要满足 **`dropped = 0`**；`smoke` 输出要满足 **`failed_patches = []`** 且覆盖层数量等于包数。

> 坑：默认档可能是 `loose`，`loose` 下 `cli mods install` 会跳过冒烟、也不判验证记录，看起来"全装成功"其实什么都没验。**验证一定要显式切 `strict` 或加 `--ext-mode strict`。**

## 5. 批量改造脚本

22 个包、284 条补丁，手工改必然漏。本次用的脚本：`_build_tools/adapt47_pack.py`（约 240 行，无第三方依赖）。

它做四件事，**不改任何功能逻辑**：

1. `text_patches` / `data_patches` 的 `find`/`replace` 换行归一（CRLF → LF）；
2. 补 `sources` 三字段（保持原 schema）；
3. 清掉根目录不被 `files[]` 引用的 zip；
4. 逐包跑 `check` → 过了才 `seal`，产物改回原名。

用法：

```bash
python adapt47_pack.py <源目录> \
  --out "<输出目录>" \
  --tools "<启动器>/扩展开发文档/tools" \
  [--only 关键字] [--exclude 关键字 ...]
```

核心三步（可以照抄进自己的脚本）：

```python
# 1) 换行归一
for p in data.get("text_patches") or []:
    for k in ("find", "replace"):
        v = p.get(k)
        if isinstance(v, str) and "\r" in v:
            p[k] = v.replace("\r\n", "\n")

# 2) 补 sources（sha 必须取 zip 文件本身的）
data["sources"] = {
    "name": "sources-4.7.zip",
    "sha256": hashlib.sha256((launcher / "baseline/sources-4.7.zip").read_bytes()).hexdigest(),
    "line": "4.7",
}

# 3) 重打包时同时写两份清单名，兼容只认其中一份的加载器
zout.writestr("manifest-47.v2.json", blob)
zout.writestr("extension.json", blob)
```

> 脚本里 `_适配报告.json` 的 `crlf_fixed` 列曾因字典覆盖恒为 0（`rebuild()` 的 stats 覆盖了 `sanitize()` 的返回值），现已修正；判断是否真有 CRLF 请以源包实测为准，不要只看报告那一列。

## 7. 冲突处置决策树

```
两个包改同一处
├─ 语义真的冲突？
│  ├─ 否，只是锚点框大了
│  │   └─ 收窄 find（缩到单行）或加 scope → 重跑 check --pair 确认变 0 条 PAIR-01
│  └─ 是
│      ├─ 有明确优先级、且两包都需要 → 写接管三件套（下方）
│      └─ 一方有硬伤（性能/维护/许可）→ 二选一，另一个不进产物，通知作者重适配
└─ 玩家侧临时处置：扩展页逐项选择 → 写进 config/decisions.json（不持久到包里）
```

**接管三件套**（缺一不可，`units.authorized()` 严格校验）：

```jsonc
// 清单顶层：声明依赖被接管方
"requires": [{ "id": "mch.treasure_dup" }],

// 补丁上：点名接管 + 前置断言
{
  "target": "scripts/slice_monster.gd",
  "find": "\tif not boss or attack_tick < 0 or hp == 0:",
  "replace": "...",
  "expect_count": 1,
  "overrides": ["mch.treasure_dup"],
  "expect_sha256": "<这条补丁所依据的文本指纹>"
}
```

三条件缺任一，接管无效，严格档照剔：

```
mch.xxx 没有声明接管 mch.treasure_dup
mch.xxx 的 requires 里没有 mch.treasure_dup
mch.xxx 的接管没有带 expect（无法校验前值）
```

> 不写 `expect` 的"接管"等于"后装即赢"，所以工具不认。

## 8. 给启动器维护者：工具链待修的四处

按影响面排序。都是小改动，但每处都在本次适配里真实咬过人。

### 8.1 `patcher._replace_in` 只做单向换行容错

`app/core/ext/patcher.py:149`：

```python
if "\n" in needle and "\r" not in needle:   # 只处理「LF 锚点 + CRLF 源码」
```

**建议**：在 `apply_text` 入口把 `find`/`replace` 的 `\r\n` 归一成 `\n`，一次改，所有包受益。当前只能靠打包侧规避，而"打包侧"包括第三方工具，控制不住。

### 8.2 `jjm_pack.py::_check_patch_anchors` 没归一锚点

源码侧 `_source_text_from_zip` 做了 `text.replace("\r\n", "\n")`，锚点侧没做，于是报错信息写的是"基线改过了"，实际是"换行风格不对"。误导排查方向。

**建议**：比对前 `find = find.replace("\r\n", "\n")`；顺便在 `PATCH-01` 的文案里区分"0 命中"与"0 命中（疑似 CRLF 锚点）"。

### 8.3 `_fits_launcher` 不接受 schema 4

`app/core/ext/enable.py:157` 只认 1/2/3，与《4.7-mod 开发规范》声明的 schema 4 冲突。

**建议**：要么放开到 4，要么把规范改成"本版 schema 3"。目前是"文档教 4、代码拒 4"，作者按文档做反而装不上。

### 8.4 `sources-4.7.json` 的 `sha256` 语义有歧义

同一个字段名，一处指 pck 指纹、一处指 zip 哈希。作者照 JSON 抄必然踩 `SRC-05`。

## 9. 钩子点共存：同一个方法被多个包挂（运行期，不拒装）

这一节和 §3.5 的「位置冲突」不是一回事：

| | 位置冲突（`PAIR-01`） | 钩子点共存（`L0-8`） |
|---|---|---|
| 发生在 | 打包/安装期 | 运行期 |
| 对象 | 同一段**源码文本** | 同一个**方法**的回调 |
| 后果 | 严格档拒装 | 装得上，但同一个 `result` 被两方改 |
| 谁判 | `jjm_pack check` / 安装闸门 | `hook_keys.compare`（扩展页体检 / `cli ext-audit`） |

### 9.1 判定只有三档

| 档位 | 含义 | 界面 |
|---|---|---|
| `safe` | 键不重叠；或重叠但双方都是读—改—写 | 不出现（收进 tooltip） |
| `unknown` | 有一方写入解析不出来 | 琥珀「需人工确认」 |
| `clash` | 有键被**直接赋值**、整份替换、或有人设 `skip_original` | 红 |

关键区别是**写入方式**，不是「有没有写同一个键」：

```gdscript
# 读—改—写：叠加。后跑的读到的就是先跑改完的值，谁先谁后只是取整差异
var base: float = float(attributes.get(attr, 0))
attributes[attr] = int(round(base * 1.5))

# 直接赋值：覆盖。谁后跑谁说了算，先跑的那份贡献直接没了
result["2013"] = int(round(float(player.get("crit_rate", 50.0)) * 100.0))
```

### 9.2 从 2026-11-13 起，分析器会「跟随静态调用」

以前只扫回调函数体本身，所以下面这种写法一律报 `unknown`：

```gdscript
# main.gd
const Core = preload("guard_core.gd")

func _on_attributes(context: Dictionary) -> void:
	var result = context.get("result")
	if not (result is Dictionary):
		return
	Core.apply_to_live(result)          # ← 写入在另一个文件里
```

现在会做四件事：

1. **认 `static func`**。宠物守护的 `guard_core.gd` 整个文件都是 `static func`，
   旧函数头正则只认行首 `func`，那个文件在分析器眼里一个函数都没有。
2. **跟随 `preload` / `class_name` 的跨文件调用**，顺着 `X.y(...)` 逐层展开
   （默认 4 层，单点最多 40 个函数体）。
3. **展开常量表里的键**。键常常不是字面量：

   ```gdscript
   const SLOTS := [{"attr": "2005"}, {"attr": "2007"}, ...]
   var attr: String = SLOTS[index].attr
   _term_attrs.append(attr)              # 存进成员数组
   var attr: String = _term_attrs[index] # 再读出来
   attributes[attr] = ...                # 键就是它
   ```

4. **区分读—改—写与直接赋值**，并把覆盖型写入的触发条件写进结论。

### 9.3 实测：宠物守护 × 更好的体验

| | 键 |
|---|---|
| `author.pet_guard` | 2005、2007、2008、2009、2010、2013 |
| `jjxf.better_experience` | 2005、2006、2007、2008、2009、2010、2013、2017 |
| 重叠 | 2005、2007、2008、2009、2010、2013（6 个） |

改动前：`author.pet_guard 的写入没解析出来，需人工确认`。
改动后：6 个重叠键里 5 个是读—改—写（叠加）；只有 `2013` 是直接赋值 ——

```
存在真正重叠：键 2013 被 jjxf.better_experience
（仅在 if bool(player.get("force_crit", false)) 时）直接赋值（不看当前值），
会覆盖同点其它扩展对它的加成
```

也就是说：**不开「强制暴击率」就没有任何影响**；开了才会盖掉宠物守护的暴击加成。
这条结论能直接照着做决定，而「需人工确认」不能。

### 9.4 作者该怎么做

- **写 `result` 一律用读—改—写**：`result[k] = f(result.get(k, 默认值))`。
  这样和别人的加成天然叠加，也不会被判冲突。
- **不要整份替换**（`context["result"] = {}`、`= 新建的空字典`）：直接判 `clash`，
  因为任何键都可能被清掉。
- **键名不要藏在运行期数据里**：`for key in 玩家配置表: result[key] = ...`
  分析器枚举不出键，只能判 `unknown`。要可判定就用常量表（`const KEYS := [...]`）。
- **`context["skip_original"] = true` 要谨慎**：它会跳过原函数，并让**排在后面的
  同点回调整个不执行**。静态分析看不出触发条件，所以一律报 `clash`；
  真要用，就在包说明里写清「只在什么场景下触发」。

### 9.5 已知边界（仍会报 `unknown`）

- 键名由运行期数据决定（上面的 `for key in 配置表`）；
- 通过 `api.get_service("别的包")` 拿到对象再调方法；
- 字符串拼接出来的键（`result["20" + suffix]`）；
- 只存在于 `.gdextension` / 预编译 `.gdc` 里的逻辑。

这几类不是「分析器偷懒」，是静态上真的看不到。遇到就人工看一眼，
不要因为面板是琥珀色就当成故障。
