# 扩展打包与发布手册（1.7 / 通用）

> 适用：4.6 与 4.7 两条内置线，以及未来的自定义线
> 工具：`tools/jjm_pack.py`（规范版本 1.7，schema 4）
> 先读你那条线的开发规范：`4.6-mod/4.6-mod开发规范.md` / `4.7-mod/4.7-mod开发规范.md`

---

## 0. 打包前必须接受的五个事实

1. **mod 是按线安装的**。4.6 的包只能装 4.6；4.7 的包只能装 4.7。想两线都支持，出两份清单。
2. **每条线有独立的覆盖层、清单副本、启用状态**。装 4.7 不会改动 4.6，反之亦然。
3. **所有基线都靠源码兜底**。启动器自动读 `baseline/sources-<line>.zip`；你不需要把原版脚本打进包，但**必须声明**用的是哪份源码。
4. **首次导入显示「待插桩」是正常流程**。插桩发生在启动时，启动成功后才变「已就绪」。
5. **「安装成功」≠「实际生效」**。前者只看文件层，后者要启动一次、看状态是否翻成已就绪。

## 1. 包结构与命名

### 1.1 单包

```
me.my_ext-1.0.0.zip
├─ extension.json          ← 必须在根目录
├─ payload/                ← 载荷（名字随意）
└─ README.md
```

### 1.2 双线包

```
me.my_ext-1.2.0.zip
├─ manifest-46.v2.json     ← 4.6 用
├─ manifest-47.v2.json     ← 4.7 用
└─ payload/                ← 两线共用
```

启动器按目标线取对应清单；找不到就按包声明拒绝。

### 1.3 合集

```
合集-2026.11.zip
├─ a.zip
├─ b.zip
└─ c.zip
```

外层不能有 `extension.json`。合集允许部分成功，失败成员单独报告。

## 2. 清单（schema 4）

```jsonc
{
  "schema": 4,
  "id": "me.my_ext",
  "name": "我的扩展",
  "version": "1.0.0",
  "author": "作者名",
  "kind": "extension",
  "baseline": { "id": "jjxf.v1.45", "engine": { "line": "4.6" } },
  "sources": {
    "name": "sources-4.6.zip",
    "sha256": "…",
    "line": "4.6"
  },
  "priority": 50,
  "requires": [],
  "conflicts": [],
  "load_after": [],
  "claims": [],
  "files": [],
  "data_patches": [],
  "text_patches": [],
  "method_hooks": []
}
```

### 2.1 `sources` 是强制的（有条件）

| 包内容 | 要不要 `sources` |
|---|---|
| 只有 `files` / `data_patches` | 不用 |
| 有 `text_patches` 或 `method_hooks` | **必须**（schema 4） |

三字段：

| 字段 | 含义 | 校验 |
|---|---|---|
| `name` | 源码包文件名 | 与本机不一致只警告（内容一致时） |
| `sha256` | 源码包内容哈希 | 不一致 → **拒装** |
| `line` | 源码所属线 | 与 `engine.line` 不一致 → **拒装** |

用工具生成，不要手抄：

```bash
python tools/jjm_pack.py manifest 我的扩展/ --id me.my_ext --name "我的扩展" --line 4.6
```

### 2.2 机读契约

上面这份签名的权威定义在 `schemas/extension.v4.schema.json`（draft-07）。
`extension.v3.schema.json` 是它的上一个版本，仍然有效（存量包大量是 v3），
但新包请用 v4。

| 文件 | 用于 |
|---|---|
| `schemas/extension.v4.schema.json` | 新包。`schema` 常量 4；有 `text_patches`/`method_hooks` 时 `sources` 条件必填（`if/then`）。 |
| `schemas/extension.v3.schema.json` | 存量包。能力与 v4 相同，只是 `sources` 不强制。 |
| `schemas/extension.v2.schema.json` | 老包，仅供兼容性测试。 |

> 运行时真正执行校验的是 `app/core/ext/manifest.py`（手写，报 `sources.*` 等
> 错误码）；schema 文件是**给作者和工具看的同一份契约**。
> `tests/test_schema_v4.py` 会核对两者不跑偏。

### 2.3 旧包（schema≤3）怎么办

- 仍然能装：没有 `sources` 只给一条警告。
- 但新发布的包一律建议 schema 4 + `sources`；否则换一台机器/换一个本体会暴露「锚点命中但改错位置」。

## 3. 源码兜底：启动器到底怎么取原文

```
1. 设置里的反解工程
2. 剧情覆盖层（仅 4.7）
3. 基线 pck 里本来就是 .gd 的文件
4. baseline/sources-<line>.zip     ← 发布包自带，玩家不需要另配
5. 已安装扩展的覆盖层（用于给别人的 mod 打补丁）
```

对应到打包：

- **不要**把原版 `scripts/*.gd` 打进包来「自带基底」。1.7 起不需要，而且会覆盖基线、冲掉别人的补丁。
- 目标脚本只要在第 2/3/4 层里存在，`check` 就会用 `SELF-04` 放行。
- 目标脚本只在**别人的扩展**里（第 5 层）时，必须写 `requires`，否则取不到原文。

### 3.1 硬闸门（两档都拦）

| 条件 | 结果 |
|---|---|
| 本条线没有可信源码 + 包依赖源码 | 拒装（`install.no_source`） |
| 随包源码与本体指纹不符（换过构建） | 拒装 |
| 启动时发现要插桩但源码被删 | 中止启动并说明原因 |

宽松档只放宽「内容问题」，不放宽「根本没有原文」。

## 4. 生命周期：从导入到生效

```
拖入 zip
  ↓
静态校验（清单 / 补丁锚点 / 钩子目标 / 源码声明）
  ↓
生成 overlay-<线>.pck，写入注册表
  ↓
界面状态：待插桩（有 method_hooks）或 已就绪（纯覆盖层）
  ↓
启动游戏：组装 overlay → 插桩层 → sources 兜底层
  ↓
进程稳定运行 5 秒
  ↓
界面状态：已就绪  ← 这才代表钩子真的注册上了
```

### 4.1 为什么要等启动

插桩必须基于**合并后的最终脚本**做（overlay 可能改了同一个文件）。安装阶段没有这个上下文，所以只能标记「待插桩」。

### 4.2 什么时候不会翻成已就绪

- 钩子目标脚本不在源码里（`找不到 xxx 的源码，跳过插桩`）
- 方法名写错（`xxx 未发生变化（方法名可能不对）`）
- 源码指纹不符导致整层被跳过

这些都会留在启动日志里；状态保持「待插桩」是**诚实**，不是 bug。

## 5. 分线隔离的存储约定

| 对象 | 4.6 | 4.7 | 自定义线 |
|---|---|---|---|
| 覆盖层 | `packs/<id>/overlay-46.pck` | `overlay-47.pck` | `overlay-custom_<id>.pck` |
| 清单副本 | `manifest-46.v2.json` | `manifest-47.v2.json` | `manifest-custom_<id>.v2.json` |
| 注册表 | `lines["4.6"]` | `lines["4.7"]` | `lines["custom:<id>"]` |
| 启用位 | `lines["4.6"].enabled` | `lines["4.7"].enabled` | 同左 |

规则：

- 线 id 进文件名前必须过 `paths.line_tag()`（把 `custom:abc` 变成 `custom_abc`，冒号在 Windows 非法）。
- **不要**手工改 `config/extensions.json` 的 `lines` 结构；界面与 CLI 都按这个结构读写。
- 只卸载一条线用 `uninstall_line`（界面：卸载时选「只卸载当前线」），不要删整个目录。

## 6. 自检流程

```bash
# 1) 结构 / 清单 / 补丁 / 钩子 / 源码 / 联机
python tools/jjm_pack.py check 我的包.zip --line 4.6

# 2) 与已装包一起能不能过（严格档口径）
python tools/jjm_pack.py verify 我的包.zip --line 4.6 --with 已装A.zip --with 已装B.zip

# 3) 两个包会不会抢同一处
python tools/jjm_pack.py check 我的包.zip --pair 别人的包.zip

# 4) 打包 / 封验证标记
python tools/jjm_pack.py pack 我的扩展/ -o 我的包.zip
python tools/jjm_pack.py seal 我的包.zip
```

### 6.1 常见错误码

| 码 | 含义 | 处理 |
|---|---|---|
| `MAN-02` | schema 不支持 | 写 `4`（或 3，新包不推荐） |
| `MAN-06/07` | 基线 / 引擎线与包不匹配 | 检查 `baseline.id` 与 `engine.line` |
| `SRC-01` | schema 4 缺 `sources` | 用 `manifest` 重新生成 |
| `SRC-02` | `sources.line` 与 `engine.line` 不一致 | 改清单 |
| `SRC-05` | `sources.sha256` 与本机源码不符 | 按本线源码重算补丁 |
| `SELF-01` | 补丁目标既不在包里也不在源码里 | 写 `requires` 或换目标 |
| `SELF-04` | 目标由随包源码兜底（通过） | 无需处理 |
| `PATCH-xx` | 锚点命中数与 `expect_count` 不符 | 重算锚点 / 用 `scope` |
| `HOOK-xx` | 钩子方法在源码里不存在 | 改方法名或目标脚本 |
