# 自定义基线导入准则（源码交付细则）

> 适用对象：希望自己发布的改版**支持方法钩子 / 插桩类 mod** 的改版创作者。
> 只做纯资源、数据覆盖的改版，交一份 `line.json` 描述就够了
> （见《自定义基线接入手册》）：本文可以跳过。
>
> **本文是《自定义基线接入手册》§5 的展开**——登记流程、分档、`line.json` 字段在
> 那篇；这里只讲「源码基线要交成什么样才收」。
>
> 配套规范：`schemas/custom_line.v1.schema.json`　验收器：`app/core/custom_baseline.py`
> 参考样例：`_custom_lab/demo_baseline/`（用 4.7 正典材料生成，可直接跑校验）

---

## 0 一句话：为什么必须交源码

启动器的插桩层要把 `dispatch_before` / `dispatch_after` **写进原脚本的明文
`.gd`**，再打成一份覆盖层，让 mod 的 `method_hooks` 能挂到真实方法上。

改版本体里通常只有 `.gdc` 编译字节码，**字节码改写不了**；只给一份
「有哪些路径」的索引也改写不了。所以想支持插桩类 mod，创作者必须自己提供
反解出来的明文脚本。

但「交了源码」不等于「能用」。拿别的工程、别的版本的源码凑数，插桩产物会
盖到错误的脚本上，表现是黑屏或改动静默失效。

**同一条规矩在两条内置线上已经是硬约束（1.7 起）**：每条线随包带
`baseline/sources-<line>.zip` + `sources-<line>.json` 指纹，启动器**自动**选用
当前线的那一份，不需要任何人手动指定路径；本体指纹（sha256 / exe 大小 /
pck 大小 / 条目数）不符时**不使用**这份源码，带补丁或钩子的包会被直接拒装。
本文把这条规矩泛化到自定义线，并做成可执行的验收器。

> 两者的区别：内置线的源码由启动器自带（作者不用管）；自定义线的源码
> **必须你自己交**，启动器不替创作者反解、不逆向 3GB 本体、不补全没交的脚本。

## 1 需要交什么

| 项 | 必需 | 说明 |
|---|---|---|
| `baseline.json` | ✅ | 元数据：绑定本体指纹、引擎线、各目录相对路径 |
| `sources/` | ✅ | **明文 `.gd` 脚本**，路径必须与本体 `res://` 路径一致 |
| `index.json` | ✅ | 能力/锚点索引；与 `line.json` 的 `source_index` 同一份格式 |
| `project.godot` | 建议 | 工程配置，便于日后核对导出设置；不参与当前校验 |
| 反解工程产物 | 自备 | GDRE / Godot RE Tools 等，用什么工具由创作者决定 |

**不收**：`.gdc` 字节码、`.pck` 本体副本、只有路径没有正文的清单、
从别的游戏/别的版本拷来的脚本。

### 目录结构

```
my-rebrand-baseline/
├── baseline.json
├── index.json
├── project.godot            # 建议
└── sources/
    └── scripts/
        ├── game.gd
        ├── equipment_panel.gd
        └── ...              # 至少要覆盖 line.json 里声明过的能力目标
```

`sources/` 下的相对路径要能直接对应本体条目：
`sources/scripts/game.gd` ↔ 本体 `scripts/game.gd` 或 `scripts/game.gdc`。

## 2 `baseline.json` 字段

```json
{
  "schema": 1,
  "identity_hash": "<启动器身份闸门算出的指纹>",
  "engine_line": "4.7",
  "game_version": "旋风改版 2.0",
  "publisher": "改版作者",
  "source_dir": "sources",
  "index": "index.json",
  "note": "GDRE 反解自本体 2.0，脚本路径与 res:// 一致"
}
```

- `identity_hash` **必填且必须与本体一致**。它由启动器闸门扫描本体内容算出，
  创作者自己编不出来——用 `cli custom-baseline status` 或让启动器导出。
  这条是防止把 A 改版的源码挂到 B 改版上。
- `engine_line`：`4.6` 或 `4.7`，与闸门按 `pack_version` 判定的一致。
- `source_dir` / `index` 可省略，缺省就是 `sources` / `index.json`。

---

## 3 `index.json` 格式

与 `line.json` 的 `source_index` 指向的是同一份结构：

```json
{
  "files": ["scripts/game.gd", "scripts/equipment_panel.gd"],
  "symbols": {
    "scripts/game.gd": ["combat_power", "equipment_changed", "character_attributes"]
  },
  "anchors": {
    "scripts/game.gd": ["func combat_power(", "func character_attributes("]
  }
}
```

- `files`：本线提供源码的脚本路径（也用于 `line.json` 的能力校验）；
- `symbols`：源码里真实存在的 `func` / `signal` 名字；
- `anchors`：补丁锚点原文，**必须是源码里能逐字找到的片段**。

三者都会逐项对着 `sources/` 里的正文复核，填了不存在的名字或锚点直接判不通过。

## 4 验收规则（B0–B5，全部通过才登记）

| 编号 | 检查 | 不通过常见原因 |
|---|---|---|
| B0 | `baseline.json` 的 `identity_hash` / `engine_line` 与闸门实测一致 | 换了本体、抄了别人的描述 |
| B1 | `sources/` 有明文 `.gd`，UTF-8、非空、含 `extends`/`func`/`signal` 等特征 | 只交了 `.gdc`、空文件、二进制 |
| B2 | `index.json` 的 `files` / `symbols` / `anchors` 在源码里逐项查得到 | 索引是手编的、脚本改过没同步索引 |
| B3 | 源码脚本能在本体 pck 索引里对应上，命中率 **≥ 80%** | 拿别的项目 / 别的版本源码凑数 |
| B4 | `line.json` 声明的 `method` / `hook` 能力目标脚本都交了源码 | 声明了 `Game.combat_power` 却没给 `game.gd` |
| B5 | 源码正文不含联机协议痕迹（复用 `netguard` 规则） | 源码里有 ENet / WebSocket / IP:端口等 |

B3 是这套准则的核心：**描述可以自己写，内容必须与本体对得上**。
B5 延续「本启动器只做单机，不支持联机接入」，交源码也不能绕过。

## 5 导入流程

创作者把上面那个目录随改版一起分发，玩家（或创作者自查）执行：

```bash
# 1) 先只校验，不改任何文件；打印 B0–B5 的逐项结果
New\ state\ launcher.exe cli custom-baseline verify <基线目录> \
    --line custom:<线ID> --game <改版本体文件>

# 2) 校验通过后登记（写 config/custom_baselines.json）
New\ state\ launcher.exe cli custom-baseline import <基线目录> \
    --line custom:<线ID> --game <改版本体文件>

# 3) 随时查状态
New\ state\ launcher.exe cli custom-baseline status --line custom:<线ID>
```

登记不是「一次性信任」：每次启动协商都会重算源码摘要并比对本体指纹，
**源码被改过、本体被换过、索引失效，都会自动退回未导入状态**，必须重新导入。

## 6 验收通过后获得什么 / 还没获得什么

**获得**：该自定义线被标记为 `baseline_ready`，协商报告与界面右栏会显示
「已导入可插桩基线（N 个脚本）」；后续插桩层生成器直接消费 `source_dir`，
不用再向创作者要材料。

**还没获得**：**插桩层的实际生成尚未接入自定义线**。在接入之前，带
`method_hooks` 的扩展仍然会被跳过，报告里会写明「基线已就绪，插桩层生成器
待接入」——绝不静默挂载。这是刻意留的边界：宁可明确跳过，也不要出现
「显示装载成功、钩子其实没人调用」（战力系统 mod 在 4.7 上就是这个坑）。

纯资源/数据覆盖层、带 `scripts.entry` 但不含方法钩子的扩展，
不依赖基线，导入与否都能按 `line.json` 的能力协商挂载。

## 7 常见失败与修法

| 报错 | 修法 |
|---|---|
| `identity_hash 与改版本体不符` | 用当前本体重新导出指纹，别复用旧改版的 `baseline.json` |
| `只有 xx% 的源码脚本能在本体里找到对应条目` | 路径要按 `res://` 原样摆放；确认反解的是**这一份**本体 |
| `符号 xxx 在源码里找不到` | `index.json` 别手写，从明文脚本里扫 `func` / `signal` 生成 |
| `锚点 ... 在源码里找不到` | 锚点必须是源码里逐字存在的片段，含缩进与参数 |
| `含联机协议` | 本启动器不支持联机接入，删掉相关脚本或改用自带联机的游戏版本 |
| `源码内容已变，需重新校验导入` | 改完脚本后重跑 `import` |

## 8 责任边界

- 反解工程、源码、能力/锚点索引**全部由改版创作者自行提供**；启动器不生产、
  不逆向、不补全，也不为源码的版权、正确性、安全性背书。
- 身份与一致性校验只回答「这份源码是不是这个改版的」，**不构成**无恶意代码、
  无联机行为、不破坏存档的保证。
- 校验通过也不代表扩展必然兼容，组合冲突仍需自行验证。
- 本启动器只做单机，描述、扩展、基线任一层出现联机协议都不予接入。

## 9 交之前自检清单

- [ ] `sources/` 里是**明文 `.gd`**，不是 `.gdc`
- [ ] 路径与本体 `res://` 一致，`scripts/game.gd` 这类能在本体里找到对应条目
- [ ] `index.json` 的 `files` / `symbols` / `anchors` 是从源码生成的，不是手编
- [ ] `line.json` 声明的每个 `method` / `hook` 能力目标都交了源码
- [ ] `baseline.json` 的 `identity_hash` 来自**当前**本体
- [ ] 源码里没有 ENet / WebSocket / 直连 IP 等联机协议
- [ ] 跑过 `custom-baseline verify`，结果为「通过、0 错误」
