# 自定义基线扩展开发手册

> 适用：已经完成《自定义基线接入手册》的改版创作者，准备让扩展作者为**你的线**开发 mod。
> 状态：**1.7 为预留能力**。自定义线目前只到 `probe-only`，插桩层未接入；
> 本文定义的是开放后的契约与现在就能做的准备工作，避免将来推倒重来。

---

## 0. 先明确边界

| 能力 | 4.6 / 4.7 内置线 | 自定义线（1.7） |
|---|---|---|
| 启动改版 | — | ✅ |
| 存档隔离 | ✅ | ✅ |
| 纯资源/数据覆盖类扩展 | ✅ | ⚠️ 未开放装配 |
| 方法钩子插桩 | ✅ | ❌ 未接入（会明确跳过） |
| 按线安装/启用/卸载 | ✅ | 存储层已按线隔离，装配层未开放 |

**不要发布声称「支持自定义线 mod」的扩展包。** 玩家装上去只会得到「不在此线」或
「插桩被跳过」，那是误导。

---

## 1. 一条自定义线的身份

| 标识 | 值 | 用途 |
|---|---|---|
| 线 id | `custom:<uuid>` | 配置键、注册表 `lines` 的键 |
| 文件名标签 | `paths.line_tag()` → `custom_<uuid>` | 覆盖层/清单/缓存文件名 |
| 基线 id | `identity.baseline`（当前固定 `jjxf.v1.45`） | 清单里的 `baseline.id` |
| 引擎线 | `identity.engine_line`（4.6 / 4.7） | 决定底座引擎与 pack 版本 |

`uuid` 由启动器登记时生成，不要自己编。扩展作者需要从你这里拿到：

```jsonc
{
  "line_id": "custom:3f2a…",
  "line_tag": "custom_3f2a…",
  "engine_line": "4.7",
  "baseline": "jjxf.v1.45",
  "sources_sha256": "你交付的反解源码摘要（custom_baselines.json 里有）"
}
```

## 2. 存储隔离契约（已经生效的部分）

即使装配层还没开放，下面这些规则现在就必须遵守，否则开放时会互相污染：

1. **一条线一份覆盖层**：`packs/<扩展 id>/overlay-custom_<uuid>.pck`。
2. **一条线一份清单副本**：`manifest-custom_<uuid>.v2.json`。
3. **启用位按线独立**：`lines["custom:<uuid>"].enabled`。
4. **卸载按线**：只删本线的覆盖层与清单副本；`lines` 空了才删整个目录。
5. **插桩缓存按线**：`cache/instrumented/<key>.json` 里记录 `line`，切换线不会非法复用。

对应代码：`app/core/ext/service.py`（`install(target_line=…)`、`set_enabled(…, line=…)`、
`uninstall_line`）、`app/core/paths.py::line_tag`。

---

## 3. 扩展包清单（开放后的写法）

自定义线的扩展包与内置线同构，只是 `baseline.engine.line` 要写自定义线 id：

```jsonc
{
  "schema": 4,
  "id": "me.my_custom_mod",
  "name": "我的改版扩展",
  "version": "1.0.0",
  "baseline": {
    "id": "jjxf.v1.45",
    "engine": { "line": "custom:3f2a…" }
  },
  "sources": {
    "name": "my_line_sources.zip",
    "sha256": "你这条线反解源码的 sha256",
    "line": "custom:3f2a…"
  },
  "files": [],
  "data_patches": [],
  "text_patches": [],
  "method_hooks": []
}
```

> 现状（1.7）：清单解析本身不限制 `engine.line` 的取值，但**安装时会把
> `engine.line` 与目标线逐字比对**，不一致就报「只适配 <线>」并拒绝；而界面目前
> 只提供 4.6 / 4.7 两个安装入口。所以写成 `custom:…` 的包现在装不进去 —— 这是
> 预期行为，不是配置错了。开放自定义线时要同步开安装入口与 `sources` 摘要核对。

---

## 4. 源码契约：扩展作者按哪份原文算锚点

自定义线的源码**由创作者交付并验收**（B0–B5），启动器按下面的顺序取：

```
1. 创作者的反解工程（config/custom_baselines.json 登记）
2. 本体 pck 里的明文 .gd（通常没有）
3. 已安装扩展的覆盖层
```

因此：

- 扩展作者必须拿到**你验收通过的那份 `sources/`**（或其打包 zip），不能拿 4.6/4.7
  的官方源码凑数——脚本不同，锚点必错。
- `sources.sha256` 要写**你这份源码**的摘要，不是内置线的。
- 你更新源码（改版升级）必须升 `version` 并重新验收；扩展作者要按新源码重算补丁。

## 5. 能力声明与扩展的对应关系

`line.json` 的 `capabilities[]` 是「这条线允许扩展挂什么」的白名单：

| 扩展侧 | 线侧要求 |
|---|---|
| `method_hooks[].target/method` | `capabilities` 里有 `kind=method` 且 `target`/`symbol` 匹配 |
| 事件/信号订阅 | `kind=signal` |
| 锚点补丁 | `anchors[]` 里有对应原文 |
| 纯资源覆盖 | `kind=resource`（`overlay.mount`） |

没声明的能力，扩展不应依赖。启动器在 `full` 档会按声明协商；声明了但源码里没有，
`line.json` 校验就过不了（B2/B4）。

---

## 6. 现在就能做的准备

1. 用《自定义基线接入手册》把 `line.json` 与反解源码基线跑通 B0–B5。
2. 把扩展作者需要的三样东西打包给他们：
   - `line_id` / `line_tag` / `engine_line`
   - 验收通过的 `sources/`（zip + sha256）
   - `capabilities` 白名单
3. 让作者先用 `jjm_pack.py check` 的**内置线源码**验证包结构；等自定义线开放后
   再把 `--line` 换成你的线，重跑锚点校验。
4. 不要提前发布「支持我的改版」的扩展；等启动器版本说明里明确写了「自定义线装配已开放」。

---

## 7. 常见问题

| 问题 | 回答 |
|---|---|
| 能在自定义线上用 4.6/4.7 的包吗 | 不能。跨线硬拒绝，锚点与源码都不同 |
| 纯资源包现在能用吗 | 装配层未开放，暂时不参与挂载 |
| 方法钩子为什么被跳过 | 自定义线插桩层未接入；跳过是明确行为，不是 bug |
| 源码改了旧扩展怎么办 | 重新验收源码，让作者按新源码重算补丁并升版本 |
| 自定义线之间会互相影响吗 | 不会。覆盖层、清单、启用位、缓存都按线隔离 |
| 未来开放后要改扩展包的什么 | `engine.line` 与 `sources` 换成自定义线 id / 摘要，其余同构 |
